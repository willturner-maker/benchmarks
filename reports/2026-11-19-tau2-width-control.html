The agent-benchmark flip rate is not batching

τ²-bench flipped 45 of 238 tasks between two temperature 0 trials, and the first version of that row blamed decode batching. A control run with the operator idle says the blame was wrong: at --max-concurrency 1 the engine batched zero times — 19,439 width-1 decode batches and not one wider — and 3 of 8 sampled tasks still flipped, exactly as many as the --max-concurrency 3 replication of the same tasks.

The two control arms agree on the count (3 of 8) and almost disagree on everything else: only retail 90 is unstable in all three passes. Across all six simulations of these tasks, reward == 1 counts land anywhere from 2/6 to 5/6 — these tasks are close to coin flips, which is why two trials is the floor for publishing a τ² row and why pass^1 − pass^2 (with 2 trials, exactly the flip count) should never be read as a capability gap.

3 · What survives the control the candidate, stated as a candidate

Even in the never-batched arm, with nobody else on the engine and temperature 0, the two trials' user-simulator turns are essentially never byte-identical: airline 0/4, 0/4, 0/7 identical, retail 0/6, 1/5, 1/7. (Telecom scores higher — 14/28, 10/25 — only because its scripted confirmations repeat verbatim.) Same input → different greedy output, first visible in the user role. With reseeding already excluded (the engine ignores seed at temperature 0) and batching now excluded too, the surviving candidate is long-context numerical state: the same persistent prefix cache that served 97.3 % of the wave's prompt volume.

That is a candidate, not a proven cause, and it is bounded by earlier evidence: the 2026-11-17 verify_rows A/B found no divergence at all on a short greedy prompt (1/5 distinct = all identical), so the effect appears at 10–16 k-token contexts and not at ~100. Separating "cache state" from "unbounded greedy variance" needs a fresh-cache-vs-warm-cache arm on these same tasks, which is the next experiment for this suite.

4 · The run that got thrown out why the first attempt is not in the numbers

The first time this control ran, it ran while the operator session (this agent) was live on the same engine. The decode-width delta across its own window: b1 14,329 · b2 8,190 · b3 409 — 8,599 decode batches wider than b1 during a run that had been passed concurrency 1. Inline /status reads in that window also showed operator-size requests in spill mode, but that run carried no 10 s sampler, so the citable evidence is the status-edge delta (published alongside the record). So concurrency 1 described the τ² runner, not the engine. It reported 5 of 8 pairs agreeing. That number is used nowhere, and the reason is written into the record rather than the files deleted.
