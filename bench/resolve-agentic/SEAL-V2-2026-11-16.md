# V2 seal findings — opencode v2.3.0 (seal probes 1–10, 2026-11-16f)

Verdict: **the V2 seal is achievable and now watertight** — but only via a mechanism
that V1 never needed. Ten probes isolated three distinct V2 behaviors:

## 1. Per-cwd `opencode.json` is NOT loaded by `opencode run` (v2.3.0)
Proved three ways in `results/seal-probe{3,5,6}-*`:
- syntactically **invalid** JSON in cwd: silently accepted (rc 0)
- `model: "bogusprov/bogusmodel"` in cwd: ignored, PONG returned (with and without a git root)
- `.opencode/opencode.json` variant: ignored
- with or without `--standalone` (private server): identical non-loading
The docs (/docs/config) promise cwd + `.opencode` discovery up to filesystem root;
`opencode run` does not honor it from a non-session cwd. **Candidate upstream bug**
(V1 1.19.5 loaded per-cwd configs — waves 16b–e prove the mechanism worked there).
**Working channel:** `OPENCODE_CONFIG=/abs/path` env var — documented ("loaded between
global and project configs in precedence order"), verified loading.

## 2. `permissions` denies are NOT enforced; `policies` are
- deny-all `permissions` + MCP allow (probes 1/3/4, incl. full config via OPENCODE_CONFIG
  with policies removed — `seal-probe3-permonly`): shell, webfetch, subagent, execute ALL ran.
- `policies` (`tool.use` denies for every built-in action + `mcp.use` deny*/allow-trio +
  `skill.use` deny* + `websearch.use` deny*): hard "Blocked by configuration policy",
  applied after agent rules and saved approvals. **Probe 8/10: pool = 3 Resolve servers only;
  agent reports shell/webfetch/execute/subagent tool-absent; `seal_leaks: []`.**
- residual: one inert `skill` tool stub remains visible (no skills advertised; skill.use denied).

## 3. Instruction/context bleed (new vs V1 waves — comparability note)
- **Global `~/.config/opencode/AGENTS.md` is injected into every trial session** (probe 9/10):
  venv paths, bench locations, OpenCV wheel status — task-relevant hints. Driver now renames
  it away for the wave (`main()` try/finally) and injects a neutral per-cwd AGENTS.md
  (both load; the global one must go).
- **MCP `<mcp_instructions>` blocks** (Resolve server skill-reference text) are injected by
  connected servers. Unavoidable without removing the server; recorded as harness drift —
  V1 waves and the Claude Code wave did not get these.
- MCP pool note: with OPENCODE_CONFIG the **global** MCP servers stay connected (brave, blender)
  unless policy-denied — the `mcp.use` deny is load-bearing, the config's server list alone is not.

## Wave driver (`wave_driver_f1f2_opencode_v2.py`) final seal stack
1. `OPENCODE_CONFIG=<per-trial opencode.json>` env (providers + mcp trio w/ codemode:false + permissions + policies)
2. `--standalone` private server per trial
3. policies hard-denials (the layer that actually seals)
4. per-trial neutral AGENTS.md + global AGENTS.md renamed away for the wave duration (restored in `finally`)
5. live seal audit per trial: every `tool_use` event must start with a KEEP server prefix; violations printed + recorded in `wave_results.json` (`seal_leaks`)

## Operator web-work note
Harness `websearch` returned cancelled; harness `webfetch` is proxied. All operator web work now
goes through the **brave-search MCP** (`brave_web_search` etc., key via `~/.config/brave-search.key`)
— direct network, no proxy. Trials never see Brave (mcp.use deny + websearch.use deny).

## Addendum 2026-11-16 (LSP plugin install) — three more V2 facts, live-probed
1. **`.opencode/plugins/` auto-discovery works in run-mode across ancestors** — an ancestor
   clone is loaded into `opencode run` sessions even with `OPENCODE_CONFIG` set (the one
   project-file channel run-mode DOES honor). A repo-local clone therefore leaks plugin tools
   into every pool trial. Containment is physical: plugin lives at
   `~/tools/opencode-v2-lsp-support`, referenced only from project `opencode.json`
   (`plugins` key), which run-mode never loads. Driver guard `seal_host_hygiene()` fails
   closed if any `.opencode/plugins/` dir appears in the home or repo tree.
2. **Policies DO gate plugin-registered tools** — `plugin.use` deny (`*` or exact id) and
   `tool.use` deny `lsp`/`lsp:*` all produced NO_LSP_TOOL on a fresh server. Driver POLICIES
   now carry plugin.use deny `*` + lsp denies as backstop.
3. **Server-reuse confound (probe hygiene):** `opencode run` attaches to a per-project-dir
   server that resolves config/plugins at first launch; re-running a different
   `OPENCODE_CONFIG` in the same cwd silently inherits the first server. Any seal probe that
   reuses a cwd is invalid — always probe from a FRESH directory. (This retracted an interim
   "policies can't gate plugins" reading during today's session.)

Also verified: opencode v2.3.0 has no native lsp tool and no post-edit diagnostics even with
`lsp` configured — the community plugin (christensenjairus/opencode-v2-lsp-support @ e055c98,
unit suite PASS on node 26) remains the only path to LSP in V2.
