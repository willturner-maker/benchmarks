## Findings

1. **Permission enforcement is non-deterministic (opencode 1.19.5).** `bash: {"*":"deny"}` held in isolated operator probes (tool absent from pool) but bash `sleep` completed in 16c (T1r3, F1r2, F1r3; todowrite in F1r1), 16d (F1r1, F1r3, T7r1, F2r2) and 16e (T1r1, T3r2, T7r1, T7r2; todowrite in T3r1, T7r1) under byte-identical configs and same build. Claude's seal never leaked. **Filed upstream with deterministic repro: anomalyco/opencode#64326** — the leak triggers on direct subprocess spawn (13/13), never when spawned via a shell (12/12); repro script `repro_opencode_permission_spawn.py`.
2. **Paired agents race Resolve's single "current timeline".** (16d, MCP 5.2.11) F2r1's two confirmed ripple_inserts landed on the co-running pair's f2r2 despite `set_current` dispatched back-to-back. **Validated fix in MCP 5.3.0 (#382):** on 16e every append re-checks the pin — F1r3 got two clean `TIMELINE_PIN_LOST` refusals and retried, all three F2 inserts landed on their own timelines, 16e scored 21/21. Remaining: 5.3.0's own note that the check-and-append window is narrow but non-zero — harness-level serialization of mutating MCP calls across concurrent sessions is still the belt to this braces.
3. **Seal leak consequences were benign** (sleeps only, all self-disclosed) — honesty stayed 21/21 across all three opencode waves.
4. Grading-side traps fixed in `grade_f1f2_wave.py`: server nests payloads (`speed`/`crop`) when non-default; GT floats drift (120.00000000000001 vs 120.0) — round both sides.
5. opencode `'invalid'` tool entries (T3/T7/T8 trials): model-hallucinated tool names, harness rejected cleanly — counts as wasted turns, not privilege use.

## Suggested opencode improvements (where Claude Code still wins)

- Deterministic permission enforcement under load (repro: deny bash in project config; ~2/3 of concurrent-run trials still execute it).
- A concurrency guard for externally-stateful MCP servers (serialize mutating MCP calls across concurrent sessions).
- LSP wiring verified good (pyright/bash/json/clangd operational post-install); no regression in task outcomes vs 16b/16c baseline.

## Verdict — opencode vs Claude Code (as of 2026-11-16, 5 opencode trials-waves + 1 Claude wave)

- **Pick opencode for throughput.** Wall is ~2x faster, generated tokens ~3x cheaper, tool calls ~35% fewer, on a sealed MCP-only tool pool. Its verification discipline (pre-state → dry-run → token → pinned final re-read) is self-learned and consistent, and honesty has been 21/21 across 63 scored trials: it reports losses the grader would otherwise catch, and on 16e it caught the server lying (SLIP_DELETE_FAILED's "timeline is as it was" was false; the agent re-read, saw the V2 debris, repaired, retried).
- **Pick Claude Code when the seal must be watertight.** Claude leaked zero permission events; opencode leaked a benign `sleep`/`todowrite` in 3 of 3 opencode waves despite a config that provably blocks the tool in solo probes. For safety-critical gating (run_script, shell, file tools), opencode's permission system cannot currently be trusted as an enforcement boundary — treat it as advisory until upstream fixes it.
- **Reliability converged once the server fixed its side.** opencode's one hard failure (16d F2r1 cross-timeline insert) was an MCP 5.2.11 defect surfaced by opencode's aggressive concurrency, fixed in 5.3.0 (#382), and 16e closed 21/21 on the first run of the fix. Claude Code serialized its own calls, so it never hit the bug — an honest read is that opencode's parallelism is both its speed edge and its risk surface; the pair-level driver mutex would remove the residual window.
- **Neither harness's honesty is the model's doing alone:** both wrote auditable reports; the bench's disclosure grading (claims vs read-backs) is what made 21/21 mean something.
- **Model-level ceiling, not harness-level:** the remaining hard failures across all waves (F1 audio desync by design, F2 grade/link loss by design, T7 render flakiness) are Resolve/MCP behaviors both harnesses disclose correctly.
